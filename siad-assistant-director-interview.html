1. 1. Describe the architecture you personally own: stack, data, cache, communications, inherited choices.

Short spoken answer: I lead architecture governance and the MedIQ modernisation. The environment includes React and Node.js components, .NET APIs, PostgreSQL, Redis caching and REST integrations. I define the target architecture and govern changes. I clearly separate inherited components from decisions I made.

Expanded answer: I start with business capabilities, data ownership and system boundaries. The architecture described in my submitted assessment includes React/Node.js, C#/.NET services, PostgreSQL, Redis, containerised deployment and REST integration with enterprise systems, including Dynamics 365. My role covers target-state decisions, architecture review, security, scalability, delivery and production readiness. Some technologies and legacy constraints were inherited. I do not present every component as personally coded or selected by me. I can explain one actual decision, such as Redis caching, and its trade-offs.

Hard follow-up: Which Redis invalidation strategy did you actually use? Which MedIQ components did you personally code? What was inherited? Answer only with verified facts.

2. 2. Replace point-to-point ERP, PMS, payments and supplier APIs with a governed integration layer.

Short spoken answer: I would define systems of record and standard API contracts, then build a governed integration layer. I would use authentication, versioning, correlation IDs, idempotency, controlled retries, reconciliation and central monitoring. I have relevant SAP and Dynamics integration experience.

Expanded answer: First I map each system's owner and the business events crossing boundaries. I define contracts and canonical data rules only where they simplify integration. I use secure APIs and asynchronous messaging where appropriate. Transient failures get limited exponential backoff; validation errors go to a controlled exception process, not endless retries. Payments and bookings require idempotency, explicit states and reconciliation. Monitoring needs traces, correlation IDs, alerts and SLA dashboards. Finally, architecture reviews, change control, vendor ownership and incident RCA stop the estate from returning to uncontrolled point-to-point links.

Hard follow-up: Explain idempotency with a double-charge example. When would you use a queue? How do you prevent infinite retries?

3. 3. Six weeks before Hajj, booking API exceeds 2 seconds at projected peak load; cloud spend is over budget.

Short spoken answer: First I measure the bottleneck, not just add servers. I check database queries, cache, code, external calls and connection pools. I agree a six-week recovery plan, test each change and report capacity, risk, cost and go/no-go readiness to leadership.

Expanded answer: I would confirm the target workload and use load-test traces and production-like telemetry to find the limiting component. I would prioritise high-impact fixes: query tuning, cache effectiveness, reducing synchronous calls and scaling only where justified. In parallel I would review unit cloud cost, idle resources and necessary peak capacity. I would set readiness criteria for latency, throughput, error rate, failover and cost, then repeat load and stress tests. My executive update would show measured capacity, the forecast gap, actions, owners, remaining risks and a clear go/no-go recommendation. I would not sacrifice reliability for a cosmetic cost target.

Hard follow-up: What is p95 latency? What if the supplier API is the bottleneck? What is the rollback trigger?

4. 4. Have you built a fully remote team, and what did you get wrong the first time?

Short spoken answer: I lead a 54-person technology organisation with nine direct reports and have managed distributed delivery. I do not claim that all 54 people work fully remotely. I focus on clear ownership, measurable outcomes, written decisions and regular coaching.

Expanded answer: My experience includes multidisciplinary and distributed delivery, not a claim that my entire current organisation is fully remote. I would build a remote office around product ownership, documented architecture, clear sprint commitments, quality gates, incident accountability, one-to-ones and capacity reviews. My learning is that more meetings cannot repair unclear ownership or acceptance criteria. I would use meetings for decisions and blockers, and dashboards for status. If asked for one personal mistake, I should describe a genuine verified event rather than invent one.

Hard follow-up: What did you personally get wrong? Prepare a real incident with context, your action, outcome and lesson.

Technical deep dive · role-aligned

Ten high-priority technical follow-ups

NCA ECC vs PDPL

NCA ECC concerns Saudi essential cybersecurity controls; PDPL governs personal data obligations. I would involve legal/compliance and security specialists to map applicable controls and evidence, not assume every platform has identical obligations.

Keywords: Applicability assessment, access, logs, data retention, incident response, control evidence

SAST vs DAST

SAST checks code or binaries without running the application. DAST tests a running application from the outside. I would combine them with dependency scans, secrets checks, peer review and penetration testing.

Keywords: CI gates, false positives, remediation SLA, threat modelling

Opera Cloud / OHIP

OHIP is Oracle Hospitality Integration Platform for integrations with Oracle Hospitality services. I would validate the hotel's enabled APIs, authentication, rate limits, booking state and error semantics before designing the adapter.

Keywords: API contracts, reservation lifecycle, idempotency, reconciliation

Dynamics 365 F&O

I would treat D365 Finance and Operations as an enterprise system of record where appropriate. Integration must respect master data, financial posting states, approvals and reconciliation. I would not claim hands-on F&O configuration unless verified.

Keywords: ERP, ownership, data mapping, audit

Fastbooking / channel managers

I would verify the supplier's actual API contract and inventory rules. Booking and pricing freshness, rate limits, duplicate requests and reconciliation are core risks.

Keywords: Inventory, pricing, stale cache, contract

Booking and payment consistency

I would model booking states explicitly and use idempotency keys and reconciliation so a timeout does not cause duplicate payment or reservation. I would never assume distributed transactions across suppliers.

Keywords: State machine, timeout, compensation, reconciliation

Vendor source-code handover

Technical acceptance needs buildable source, dependency manifest, infrastructure configuration, secrets handover process, deployment and rollback guides, test evidence and support knowledge transfer.

Keywords: IP rights, CI/CD, documentation, acceptance

Release sign-off boundary

The Assistant Director approves release readiness and submits it to the IT & Digital Transformation Director for final go-live sign-off, as the job description states.

Keywords: QA, UAT, security, rollback, director approval

Hajj capacity planning

I would forecast demand, test peak concurrency and p95/p99 latency, review upstream limits and prepare fallback and incident plans. Extra cloud spend needs an evidence-based business case.

Keywords: Load test, SLO, FinOps, go/no-go

Remote engineering office

I would define product-aligned ownership, onboarding, written decisions, code review, one-to-ones, performance measures and succession planning. Distributed experience is not the same as having run a fully remote office.

Keywords: Accountability, async communication, outcome metrics
