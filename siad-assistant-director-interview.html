Technical follow-ups · Short answers
Which parts did you personally build?

I personally designed and built healthcare REST APIs. I led architecture and delivery governance for the wider platform; I did not code every component.

Why Redis?

A cache can reduce repeated database reads. I would check freshness, expiry and invalidation rules before using it.

What was inherited?

I would separate the original stack from later changes using architecture records and release history. I would not guess which component came first.

How do you protect data consistency?

The database remains the source of truth. Cached data needs clear expiry or invalidation, and critical transactions should not rely on stale cache.

2. Replace point-to-point ERP, PMS, payments and supplier APIs with a governed integration layer.

Short spoken answer: I would first map business flows and systems of record. Then I would define a governed integration layer with contracts, authentication, versioning, idempotency, reconciliation and monitoring. I led UPA's completed bi-directional SAP Strategic Medical Warehouses integration, from requirements and master-data mapping through user testing, go-live and support. I also directed the completed Dynamics 365 integration.

Technical follow-ups · Short answers
How does idempotency prevent double charging?

The client sends a unique payment key. A repeated request with the same key must return the original result, not create another charge.

When would you use a queue?

For work that can happen asynchronously, such as notifications or partner updates. I would not put an immediate booking confirmation into a queue without a clear customer status.

How do you stop endless retries?

I use a retry limit, backoff and a dead-letter queue where suitable. Then I alert the owner and reconcile the transaction.

What if payment succeeds but booking fails?

I verify both systems using transaction IDs, keep the booking pending and follow the agreed recovery or refund process.

3. Six weeks before Hajj, booking API exceeds 2 seconds at projected peak load; cloud spend is over budget.

Short spoken answer: I would measure end-to-end performance, including p95 latency, database queries, Redis cache, application code, supplier response times and cloud capacity. Then I would prioritize safe changes, run realistic peak-load tests, control spending and agree rollback and go-or-no-go criteria. My experience includes national-scale MedIQ operations, performance testing and private-cloud capacity governance. I would not claim direct Hajj booking experience.

Technical follow-ups · Short answers
What is p95 latency?

It means 95 percent of requests finish within that time. I would measure it at realistic peak traffic, not just the average.

What if the supplier API is slow?

I measure supplier latency separately, set timeouts and safe retry rules, and discuss capacity with the supplier. I would not hide a failed booking behind a success response.

How do you reduce cloud cost safely?

I review resource usage, scaling, database load and unused services. I test each change against performance before reducing capacity.

What is your rollback trigger?

A pre-agreed limit for errors, latency or failed bookings. If a release crosses that limit, we stop or roll back under the incident plan.

Who approves go-live?

I present test evidence, residual risks and a recommendation. The Director has final go-live approval under the stated role.

4. Have you built a fully remote team, and what did you get wrong the first time?

Short spoken answer: I lead a multidisciplinary technology organization of fifty-four people with nine direct reports, and previously led twenty developers in Oman. I have coordinated distributed delivery, but do not claim a fully remote organization. I would use clear ownership, written decisions, measurable results and regular coaching. A real mistake I can discuss is trusting a CRM vendor commitment without enough early technical validation. The proposed architecture later proved unsuitable for our data-center and connectivity constraints. I took responsibility and led the technical assessment of alternatives. That changed how I validate critical assumptions before delivery.

Technical follow-ups · Short answers
Have you managed a fully remote team?

I have led distributed delivery, but I cannot claim all 54 people in my current organisation work fully remotely.

How would you manage remote engineers?

I set clear owners, delivery goals, written decisions, short check-ins and regular one-to-ones. I review outcomes rather than online hours.

How do you spot poor performance remotely?

In the MedIQ replacement, we used migration checks, reconciliation, testing and a controlled cutover. I now make owners, risks and go-live evidence clear from the start. This is a lesson from delivery, not a claim that I caused a specific failure.

Technical deep dive · role-aligned

Ten high-priority technical follow-ups

NCA ECC vs PDPL

NCA ECC concerns Saudi essential cybersecurity controls; PDPL governs personal data obligations. I would involve legal/compliance and security specialists to map applicable controls and evidence, not assume every platform has identical obligations.

Keywords: Applicability assessment, access, logs, data retention, incident response, control evidence

SAST vs DAST

SAST checks code or binaries without running the application. DAST tests a running application from the outside. I would combine them with dependency scans, secrets checks, peer review and penetration testing.

Keywords: CI gates, false positives, remediation SLA, threat modelling

Opera Cloud / OHIP

OHIP is Oracle Hospitality Integration Platform for integrations with Oracle Hospitality services. I would validate the hotel's enabled APIs, authentication, rate limits, booking state and error semantics before designing the adapter.

Keywords: API contracts, reservation lifecycle, idempotency, reconciliation

Dynamics 365 F&O

I would treat D365 Finance and Operations as an enterprise system of record where appropriate. Integration must respect master data, financial posting states, approvals and reconciliation. I would not claim hands-on F&O configuration unless verified.

Keywords: ERP, ownership, data mapping, audit

Fastbooking / channel managers

I would verify the supplier's actual API contract and inventory rules. Booking and pricing freshness, rate limits, duplicate requests and reconciliation are core risks.

Keywords: Inventory, pricing, stale cache, contract

Booking and payment consistency

I would model booking states explicitly and use idempotency keys and reconciliation so a timeout does not cause duplicate payment or reservation. I would never assume distributed transactions across suppliers.

Keywords: State machine, timeout, compensation, reconciliation

Vendor source-code handover

Technical acceptance needs buildable source, dependency manifest, infrastructure configuration, secrets handover process, deployment and rollback guides, test evidence and support knowledge transfer.

Keywords: IP rights, CI/CD, documentation, acceptance

Release sign-off boundary

The Assistant Director approves release readiness and submits it to the IT & Digital Transformation Director for final go-live sign-off, as the job description states.

Keywords: QA, UAT, security, rollback, director approval

Hajj capacity planning

I would forecast demand, test peak concurrency and p95/p99 latency, review upstream limits and prepare fallback and incident plans. Extra cloud spend needs an evidence-based business case.

Keywords: Load test, SLO, FinOps, go/no-go

Remote engineering office

I would define product-aligned ownership, onboarding, written decisions, code review, one-to-ones, performance measures and succession planning. Distributed experience is not the same as having run a fully remote office.

Keywords: Accountability, async communication, outcome metrics
